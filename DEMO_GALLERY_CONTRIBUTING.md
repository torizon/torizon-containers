# Demo Gallery Contributing Guide

This guide explains how to contribute new demos to the Torizon Containers demo gallery.

## Description

The demo gallery is a feature that spans over Torizon OS and Torizon Cloud, with contributions from the Developer
Experience team. Essentially, it's a machine-generated package feed for Torizon Cloud. In the Torizon Cloud UI,
it is a Package Source named "Torizon Demo Apps". 

The intention of the Demo Gallery is that users can quickly evaluate simple applications through our update system.
The evaluation workflow is as follows:

- User installs or already has Torizon OS 7 or above installed.
- User pairs device to Torizon Cloud using the Torizon Easy Pairing app that comes pre-installed with Torizon OS 7 or above.
- Demo Apps can be deployed into the board.

## Overview

The demo gallery workflow in this repo consists of three main components:
1. **Compose files** in [`tests/composes/`](tests/composes/) - Docker Compose configurations for demos
2. **Run files** in [`tests/runs/`](tests/runs/) - Generated Docker run commands (auto-generated by CI)
3. **Test files** in [`tests/cases/`](tests/cases/) - Automated tests for validating demos
4. **Demo Gallerizator** - A service that pushes the newly generated demo gallery feed to the demo-gallery repository. This feed is then consumed by the [Delegation Publisher Repository](https://gitlab.com/toradex/torizon-cloud/delegations-publisher), which ultimately generates the "Torizon Demo Apps" package source available in Torizon Cloud.

The workflow is:
1. CI generates Docker run commands from compose files using the [decompose](https://gitlab.com/toradex/rd/torizon-core/decompose)
during the [generate job](ci-scripts/generate/generate.yml)
2. Run files are consumed during test-time by a [script](tests/helpers/read-docker-run.sh)
3. Containers are tested by the BATS framework using [Aval](https://gitlab.com/toradex/rd/torizon-core/aval) as the testing infrastructure. Tests run every night or on-demand.
3. The [Demo Gallery Repository](https://gitlab.com/toradex/rd/torizon-core/packages-and-containers/demo-gallery) is generated and pushed
using a [Python script](ci-scripts/demo-gallery/demo-gallerizator.py)
4. Delegation Publisher creates package source from feed once per day
5. Package source appears as "Torizon Demo Apps" in Torizon Cloud

## Demo Gallery structure

The demo gallery is generated as a structured repository containing canonicalized Docker Compose files and JSON metadata that serves as a contract between the demo gallery repository and the delegation-publisher repository. This structure contains all the information needed for demos to be available in Torizon Cloud as a package source.

### Processing Workflow

The demo-gallerizator performs the following transformations on the source compose files:

1. **Platform Mapping**: You will notice that we have several compose files that are identical, and this makes sense when thinking about the `platform` concept in Torizon Containers: the same software should run on Apalis iMX8 as it does on Verdin iMX8. However, due to pragmatic decisions when implementing the Demo Gallery feature, it was decided that we would have per-board apps, which means per-board Docker composef files.

To alleviate programmer fatigue, the demo-gallerizator script will map platform families to specific hardware modules:
   - `imx8` → `apalis-imx8`, `colibri-imx8x`, `verdin-imx8mm`, `verdin-imx8mp`, `smarc-imx8mp`
   - `am62` → `verdin-am62`, `sk-am62`, `sk-am62l`
   - `am62p` → `verdin-am62p`, `sk-am62p`
   - `am67a` → `beagley-ai`
   - `am69` → `aquila-am69`
   - `imx95` → `verdin-im95`, `smarc-imx95`, `aquila-imx95`
   - `sl1680` → `astra-sl1680`, `luna-sl1680`
   - `upstream` → `apalis-imx6`, `colibri-imx6`, `colibri-imx6ull`, `colibri-imx7`, `frdm-imx93`

Thus, from a single compose file for the iMX8 platform, we get board-specific composes for Apalis, Colibri, Verdin, etc.

2. **File Transformation**: Converts platform-specific compose files to hardware-specific variants:
   - Input: `chromium-imx8-compose.yml`
   - Outputs: `docker-compose-apalis-imx8.yml`, `docker-compose-verdin-imx8mm.yml`, etc.

3. **Image Canonicalization**: Uses torizoncore-builder to:
   - Remove `$REGISTRY/` prefixes from image names
   - Replace `stable-rc` tags with version numbers (currently `4`)
   - Generate `.lock.yml` files with pinned image digests
   - Replace original compose files with canonicalized versions

The demo gallery repository follows this structure:

```

│   ├── docker-compose-verdin-imx8mm.yml   # Canonicalized compose file

│   └── app.json                           # Metadata for this demo
├── qt6-wayland-examples/

│   ├── docker-compose-verdin-imx8mp.yml
│   └── app.json
└── ...
```

### JSON Metadata Structure

Each demo directory contains an `app.json` file with the following structure:

```json
{
    "packages": [
        {
            "name": "chromium-apalis-imx8",
            "filename": "docker-compose-apalis-imx8.yml",
            "version": "4"
        },
        {
            "name": "chromium-verdin-imx8mm", 
            "filename": "docker-compose-verdin-imx8mm.yml",
            "version": "4"
        },
        ...
    ]
}
```

For a complete specification of this exchange format between the Demo Gallery and the Demo Publisher repo, please refer to the Demo Publisher script.

### Canonicalized Compose Files

The canonicalized compose files have these characteristics:

- **Pinned Images**: All image references use specific digests instead of tags
- **Fully Qualified**: Complete image names without registry variables
- **Version Locked**: Specific version numbers replace floating tags
- **Hardware Specific**: Named for specific hardware modules rather than platform families

**Example canonicalized compose file:**
```yaml
services:
  weston:
    image: torizon/weston-imx8@sha256:abc123...
    # ... rest of service definition
  chromium:
    image: torizon/chromium-imx8@sha256:def456...
    # ... rest of service definition
```

## Disabling a Demo from the Gallery Feed

Sometimes a demo needs to be temporarily (or permanently) kept out of the published
feed without deleting its compose files or tests, for example while a regression is
being investigated. To do this, add an empty `.disabled` marker file to the demo's
directory under [`tests/demo-gallery-composes/`](tests/demo-gallery-composes/):

```bash
touch tests/demo-gallery-composes/your-demo-name/.disabled
```

When the Demo Gallerizator runs, it skips any app directory containing this marker
entirely: none of its compose files are copied, canonicalized, or included in the
feed pushed to the [Demo Gallery Repository](https://gitlab.com/toradex/rd/torizon-core/packages-and-containers/demo-gallery),
so it will not reach the Delegation Publisher or appear as a Torizon Demo App.

To re-enable the demo, remove the `.disabled` file. Note that this only controls
whether the demo goes live through the Demo Gallerizator; it has no effect on the
BATS tests, which keep running regardless.

## Step-by-Step Contribution Workflow

### 1. Create Compose Files

Navigate to the [`tests/composes/`](tests/composes/) directory and create a new folder for your demo:

```bash
mkdir tests/composes/your-demo-name
```

Create compose files for each supported platform using the naming convention:
- `your-<demo-name>-<platform>-compose.yml`

**Supported platforms:**
- `upstream` - Generic upstream Debian images
- `imx8` - NXP i.MX8 family SoCs
- `imx95` - NXP i.MX95 SoCs  
- `am62` - TI AM62 SoCs
- `am62p` - TI AM62p SoCs
- `am69` - TI AM69 SoCs
- `am67a` - TI AM67a SoCs
- `sl1680` - Synaptics SL1680 SoCs

**Example compose file structure:**
```yaml
# description: a description of what your demo actually does, *MUST* start with `description: ` exactly
services:
  weston:
    network_mode: host
    cap_add:
      - CAP_SYS_TTY_CONFIG
    volumes:
      - '/dev:/dev'
      - '/tmp:/tmp'
      - '/run/udev/:/run/udev/'
    device_cgroup_rules:
      - 'c 4:* rmw'
      - 'c 253:* rmw'
      - 'c 13:* rmw'
      - 'c 226:* rmw'
      - 'c 10:223 rmw'
      - 'c 199:0 rmw'
    image: '$REGISTRY/torizon/weston-imx8:stable-rc'
    command: '--developer --tty=/dev/tty7 -- --debug'

  your-demo:
    command: your-demo-command-here
    depends_on:
      - weston
    device_cgroup_rules:
      - 'c 4:* rmw'
      - 'c 13:* rmw'
      - 'c 226:* rmw'
      - 'c 199:* rmw'
    image: $REGISTRY/torizon/your-demo-imx8:stable-rc # <- NOTE THE $REGISTRY VARIABLE! We use a Proxy during test, so we MUST have this on the compose files.
    volumes:
      - '/tmp:/tmp'
      - '/var/run/dbus:/var/run/dbus'
      - '/dev/dri:/dev/dri'
```

### 2. Generate Run Files with CI

The run files are automatically generated from your compose files. **Do not create or edit them manually**.

To trigger the generation process:

1. **Commit your compose files** to your branch
2. **Set the CI variable** `CI_COMPOSE_GENERATE=true` when running the pipeline
3. **The CI will automatically:**
   - Use the [`decompose`](https://gitlab.com/toradex/rd/torizon-core/homebrew-toradex) tool to convert compose files to run files
   - Generate corresponding `.run` files in [`tests/runs/`](tests/runs/)
   - Commit the generated files back to your branch

**CI Generation Process:**
- Script: [`ci-scripts/generate/run-from-compose.sh`](ci-scripts/generate/run-from-compose.sh)
- Configuration: [`ci-scripts/generate/generate.yml`](ci-scripts/generate/generate.yml)
- Input: `tests/composes/**/*-compose.yml`
- Output: `tests/runs/**/*.run`

### 3. Write Tests

Create test files in [`tests/cases/`](tests/cases/) to validate your demo. Tests can be very simple; for example, create
a simple test that verifies that the application can run for 20 seconds with the `timeout` command.

This is imperative: simple tests are a *must*, complex tests are *optional* and should be rare. If you're test has more than
10 lines, review everything.

#### Example Test File (`your-demo.bats`):

```bash
#!/usr/bin/env bats

load ./weston-helper.sh
load ./general-helper.sh
load ./your-demo-helper.sh

setup_file() {
  setup_weston
  setup_your_demo
}

teardown_file() {
  teardown_your_demo
  teardown_weston
}

# bats test_tags=platform:imx8, platform:sl1680, platform:imx95, platform:am62, platform:am62p, platform:upstream
@test "Your demo starts successfully" {
  run -0 docker container exec your-demo your-demo-command --test
}

# bats test_tags=platform:imx8, platform:sl1680, platform:imx95, platform:am62
@test "Your demo displays content" {
  run -124 docker container exec your-demo timeout 10s your-demo-command --display-test
  echo "Demo ran for 10 seconds without crashing, terminated by timeout."
}
```

#### Example Helper File (`your-demo-helper.sh`):

```bash
#!/usr/bin/env bash

setup_your_demo() {
  docker container kill your-demo || true
  docker container rm your-demo || true
  
  if [[ "$PLATFORM_FILTER" == *imx8* ]]; then
    DOCKER_RUN="docker run -d --name your-demo $REGISTRY/torizon/your-demo-imx8:stable-rc"
  elif [[ "$PLATFORM_FILTER" == *am62* ]]; then
    DOCKER_RUN="docker run -d --name your-demo $REGISTRY/torizon/your-demo-am62:stable-rc"
  else
    DOCKER_RUN="docker run -d --name your-demo $REGISTRY/torizon/your-demo:stable-rc"
  fi
  
  eval "$DOCKER_RUN"
  sleep 5
  check_if_base_container_runs your-demo
}

teardown_your_demo() {
  cleanup_container your-demo
}
```

## File Naming Conventions

### Compose Files
- **Location:** `tests/composes/demo-name/`
- **Format:** `<demo-name>-<platform>-compose.yml`
- **Example:** `chromium-imx8-compose.yml`

### Run Files (Generated)
- **Location:** `tests/runs/demo-name/`
- **Format:** `<demo-name>-<platform>-compose.run`
- **Example:** `chromium-imx8-compose.run`

### Test Files
- **Location:** `tests/cases/`
- **Format:** `demo-name.bats` and `demo-name-helper.sh`
- **Example:** `chromium-tests-weston.bats`

## Compose File Requirements

### Essential Elements

1. **Image references** must use the `$REGISTRY` variable:
   ```yaml
   image: $REGISTRY/torizon/your-image:stable-rc
   ```

2. **Platform-specific images** should match the compose file platform:
   ```yaml
   image: $REGISTRY/torizon/your-demo-imx8:stable-rc
   ```

2. **First line should be a description** which starts with `# description: `, including the white space:
   ```yaml
   # description: a description of what your demo actually does
   image: $REGISTRY/torizon/your-demo-imx8:stable-rc
   ```
## Test Requirements

### Test Tags

Use `bats test_tags` to specify which platforms your test supports:

```bash
# bats test_tags=platform:imx8, platform:sl1680, platform:imx95, platform:am62, platform:am62p, platform:upstream
@test "Test that runs on multiple platforms" {
  # test code
}

# bats test_tags=platform:imx8
@test "Test specific to imx8 platform" {
  # test code
}
```

### Helper Functions

Use existing helper functions from [`tests/helpers/`](tests/helpers/) and [`tests/cases/`](tests/cases/):

- `setup_weston` / `teardown_weston` - Weston compositor management
- `check_if_base_container_runs` - Verify container startup
- `cleanup_container` - Clean container shutdown
- `clean_kernel_logs` / `gpu_kernel_logs` - Kernel log management

## Commit hygiene

As explained in the [README](README.md) file in this repo, we follow a standard when commiting. The contributor must be aware that every commit should comply with the following rules:

### Commit header

The commit header **must** have **at least one** tag followed by the commit title. For demo gallery contributions, the tag we use is `demo-gallery`. Every tag is followed by a **collon + space** (`: `). For example:

```bash
# This is a valid commit header
demo-gallery: add foo demo

# This is also a valid commit header
demo-gallery: imx8: add foo demo for imx8 platform

# This is invalid
add bar demo
```

### Mandatory fields in the commit message body

There are two mandatory fields that **must** be in the commit message:

- *Related-to*: this field links the commit with a valid Jira ticket. We need **at least one** of this field. When having multiple Jira tickets, each one must have its own *Related-to* line.
- *Signed-off-by*: this is a signature indicating who made the commit. We need **only one** signature per commit. The signature includes the username and the e-mail of the commit's author. You can add it to your commit by using git's `-s` flag.

Examples:

```bash
# This is a valid commit message
demo-gallery: add foo demo

This commit adds a new demo called foo

Related-to: ABCD-1234
Related-to: EFGH-5678

Signed-off-by: Jill Valentine <jill.valentine@email.com>
```

```bash
# This is not valid
demo-gallery: add bar demo

This commit adds a new demo called bar. It also deliberately fails
to add a Related-to field

Signed-off-by: John Forget-A-Lot <johnforget@email.com>
```

Notice that both required fields must follow a given format. *Related-to* entries that fail to follow the `ABCD-1234` pattern (uppercase letters + hyphen + numerals) will be rejected.

### That's a lot to remember

Don't worry, we have a git hook that will check for all these rules. **Just remember to configure them as soon as you clone this repo into your machine**. It's very simple, just run the following command from the repo's root folder:

```bash
./git-setup.sh
```

### GPG Signing
This project requires that contributors sign their commits with GPG. In order
to do that, follow [this documentation](https://docs.gitlab.com/user/project/repository/signed_commits/gpg/).

We also encourage you to configure Git to automatically GPG sign your commits,
so you can suppress the `-S` flag.

```
git config --global commit.gpgsign true
```

## CI Integration

### Triggering Run File Generation

Set the CI variable to generate run files:
```bash
# In GitLab CI/CD Variables or pipeline trigger
CI_COMPOSE_GENERATE=true
```

## Contributing Checklist

Before submitting your demo contribution:

- [ ] Created compose files for relevant platforms
- [ ] Followed naming conventions
- [ ] Run files have been generated with `CI_COMPOSE_GENERATE=true`
- [ ] Written comprehensive but simple tests
- [ ] Added appropriate platform tags
- [ ] Verified tests pass on *at least one target platform*; ie, it's ok for a test to pass on Verdin iMX8 and fail on Apalis iMX8
- [ ] Tracked the errors appropriately on Jira or somewhere else
- [ ] Updated documentation if needed
